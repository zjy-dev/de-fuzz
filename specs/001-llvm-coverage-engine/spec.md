# Feature Specification: LLVM 覆盖率驱动 Fuzz Engine 移植

**Feature Branch**: `001-llvm-coverage-engine`

**Created**: 2026-06-11

**Status**: Draft

**Input**: User description: "我现在需要把 fuzz engine 再额外写一套 llvm 的方案，之前只有 gcc 的覆盖率驱动 engine，现在我希望移植一套 llvm 的方案。参考 USENIX Security 2025 (Yang Yupeng) 论文，本项目覆盖率方案是其简化版。llvm 移植方案也只需实现简化版即可。移植只聚焦 fuzz engine 的覆盖率模块，和预言机/llm 无任何关系。"

## 背景与定位 *(context)*

DeFuzz 是一个"测编译器自身"的 LLM-driven 约束求解 fuzzer。当前覆盖率模块（`internal/coverage/`）只支持 GCC：被测对象是一个**被插桩的 GCC（`xgcc`）**，它在编译每颗 seed 时把"编译器自己运行到的源码行"写入 `.gcda`，fuzzer 用 `gcovr` 聚合成 JSON 报告，并结合 GCC 构建期 `-fdump-tree-cfg-lineno` 产出的 `.015t.cfg` 控制流图，做 CFG 引导的目标基本块（BB）选择。

本特性要新增一套**等价的 LLVM/Clang 覆盖率方案**，让 fuzz engine 既能驱动 GCC、也能驱动被插桩的 Clang/LLVM，二者在"覆盖率测量 + CFG 引导目标选择"两层功能上对齐。本移植**只**涉及覆盖率模块，与预言机（oracle）、LLM 变异、prompt 等子系统无关，不得改动它们的语义。

### 关键决策（来自澄清）

- **工具链**：采用 LLVM 原生 source-based coverage——`-fprofile-instr-generate -fcoverage-mapping` 插桩被测 Clang，运行后用 `llvm-profdata merge` + `llvm-cov export`（JSON）采集"Clang/LLVM 自身源码"的行/区域覆盖。不复用 gcov/gcovr 兼容层。
- **移植深度**：实现到"测量 + CFG 目标选择"两层，与 GCC 完全对齐，使 engine 在 LLVM 下功能等价。
- **被测目标**：对齐现有 stack-canary / 栈保护策略——被测编译器为 Clang/LLVM，插桩聚焦其栈保护实现相关源文件/Pass，便于与 GCC 结果直接对比。
- **简化范围**：仅实现论文覆盖率方案的简化版——线/区域级覆盖反馈 + 基本块级目标选择，不实现论文中的高级特性（如更复杂的反馈调度、跨编译单元全局分析等）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 用 LLVM 覆盖率测量驱动 fuzz 主循环 (Priority: P1)

研究者配置一个被插桩的 Clang/LLVM 作为被测编译器，启动 fuzz。引擎每编译一颗 seed 后，能采集到"Clang/LLVM 自身源码"的覆盖率，判断本颗 seed 是否带来新的覆盖增量，并把增量并入累计覆盖（支持断点续跑）。

**Why this priority**: 这是 LLVM 方案的最小可用核心——没有覆盖率测量，fuzz 主循环无法做"是否有新覆盖"的决策，整套引擎在 LLVM 下无法运转。

**Independent Test**: 仅提供一个被插桩的 Clang + 若干 seed，运行覆盖率测量路径，验证能生成单 seed 覆盖报告、正确判定覆盖增量、并把累计覆盖持久化到可恢复的总报告文件，无需 CFG 目标选择或 oracle 参与即可验证。

**Acceptance Scenarios**:

1. **Given** 一个被插桩的 Clang 和一颗能编译成功的 seed，**When** 引擎对该 seed 执行覆盖率测量，**Then** 系统产出该 seed 的覆盖报告，记录被测编译器源码中被命中的行/区域集合。
2. **Given** 已有累计覆盖（总报告存在），**When** 一颗新 seed 命中了此前未覆盖的源码行，**Then** 系统判定"覆盖增量为真"并将新覆盖并入累计覆盖。
3. **Given** 一颗新 seed 未带来任何新覆盖，**When** 引擎检查覆盖增量，**Then** 系统判定"无增量"，累计覆盖保持不变。
4. **Given** 上一轮 fuzz 已落盘累计覆盖，**When** 重新启动 fuzz，**Then** 系统从已存在的累计覆盖继续，而非从零开始。

### User Story 2 - LLVM 下的 CFG 引导目标选择 (Priority: P2)

研究者希望 LLVM 方案也能像 GCC 那样"挑一个高价值的未覆盖基本块作为目标"，引导 LLM 生成命中该 BB 的 seed。系统需从被测 Clang/LLVM 获取目标函数的控制流结构（基本块、后继关系、源码行号），并在其上做与 GCC 等价的目标 BB 选择。

**Why this priority**: 没有它，LLVM 方案退化为"只测量、不引导"，与 GCC 方案不对齐；但它依赖 P1 的测量结果（已覆盖行集合）才能工作，故优先级次于 P1。

**Independent Test**: 提供被测编译器目标函数的控制流结构数据与一份"已覆盖行集合"，验证系统能解析出基本块/后继/行号、在目标函数内选出一个满足"可达且含未覆盖行"的 BB，并给出权重排序——无需真实运行 LLM。

**Acceptance Scenarios**:

1. **Given** 被测 Clang/LLVM 目标函数的控制流结构，**When** 系统解析该结构，**Then** 得到与 GCC Analyzer 等价的基本块集合、后继/前驱关系、每个 BB 关联的源码行号。
2. **Given** 一份已覆盖行集合与解析后的 CFG，**When** 系统选择目标 BB，**Then** 选出的 BB 位于配置的目标函数内、至少含一行未覆盖、且可达（无前驱或至少一个前驱已被覆盖）。
3. **Given** 多个候选 BB，**When** 系统排序，**Then** 按分支因子（后继数）等价的权重优先选择，失败重试后对应 BB 权重衰减，避免死磕不可达目标。
4. **Given** 目标函数全部覆盖，**When** 系统尝试选择目标，**Then** 返回"无可选目标"信号，与 GCC 行为一致。

---

### User Story 3 - 引擎按配置在 GCC / LLVM 间切换 (Priority: P3)

研究者通过配置选择"用 GCC 还是 LLVM 覆盖率方案"，fuzz engine 的主循环、corpus、目标选择等上层逻辑无需改动即可在两套方案间切换；预言机/LLM 子系统完全不受影响。

**Why this priority**: 提升可用性与可维护性，但即便没有平滑切换，P1+P2 已能独立验证 LLVM 方案本身；故最低优先级。

**Independent Test**: 用同一套上层引擎，分别加载 GCC 配置与 LLVM 配置启动，验证两种配置都能进入 fuzz 主循环并完成至少一轮测量+目标选择，且引擎代码路径对两者一致对待覆盖率接口。

**Acceptance Scenarios**:

1. **Given** 一份 LLVM 覆盖率配置，**When** 启动 fuzz，**Then** 引擎装配 LLVM 覆盖率组件并进入主循环，无需修改 oracle/LLM/prompt 配置。
2. **Given** 一份 GCC 覆盖率配置，**When** 启动 fuzz，**Then** 现有 GCC 行为保持不变（无回归）。
3. **Given** LLVM 与 GCC 两套配置面向同一防御机制（栈保护），**When** 分别运行，**Then** 两者都通过统一的覆盖率抽象被引擎消费，covered-lines 语义一致（均为"被测编译器自身源码行"）。

### Edge Cases

- 当 seed 编译失败（被测 Clang 报错）时，覆盖率测量如何处理？（应不产生增量、不污染累计覆盖，与 GCC 行为一致。）
- 当被测编译器未真正写出原始覆盖数据（profile 文件缺失/为空）时，系统如何报错而非静默产出空覆盖？
- 当某 seed 的原始覆盖数据残留未清理时，是否会污染下一颗 seed 的测量？（每轮测量前需清理运行期覆盖产物，仅保留结构数据。）
- 当配置的目标函数在被测编译器的控制流结构中找不到时，系统如何处理（报错退出或跳过并告警）？
- 当 LLVM 覆盖数据格式与 GCC 报告格式不同时，引擎读取"已覆盖行集合"的统一入口如何屏蔽差异？
- 累计覆盖文件在中断时损坏/半写，恢复时如何避免崩溃？

## Requirements *(mandatory)*

### Functional Requirements

**覆盖率测量（对齐 GCC `Coverage` 能力）**

- **FR-001**: 系统 MUST 提供一个 LLVM 覆盖率实现，满足与 GCC 方案相同的覆盖率抽象契约（清理运行期产物、测量单 seed、判定覆盖增量、合并入累计覆盖、产出累计报告、给出覆盖统计）。
- **FR-002**: 系统 MUST 通过 LLVM 原生 source-based coverage 工具链（profile 生成 + profdata 合并 + 覆盖导出）采集**被测 Clang/LLVM 自身源码**的覆盖，而非被编译 seed 的覆盖。
- **FR-003**: 系统 MUST 在每颗 seed 测量前清理上一轮运行期覆盖产物，保留构建期结构数据，确保各 seed 测量互不污染。
- **FR-004**: 系统 MUST 为每颗 seed 产出可独立保存的单 seed 覆盖报告，并能将其合并进累计覆盖总报告。
- **FR-005**: 系统 MUST 能判断一颗 seed 的覆盖报告相对累计覆盖是否存在增量，并在存在增量时返回可供上层使用的增量摘要（新覆盖行数等）。
- **FR-006**: 系统 MUST 将累计覆盖持久化为可恢复的总报告文件，支持中断后从该文件继续累计（断点续跑）。
- **FR-007**: 系统 MUST 提供从覆盖报告抽取"已覆盖行集合（被测编译器源码 file:line）"的能力，并支持按配置的目标文件/函数过滤，使行集合只包含关心的目标函数。
- **FR-008**: 系统 MUST 提供累计覆盖统计（覆盖行数/总行数/覆盖百分比、函数覆盖等可得指标），供运行摘要展示。

**CFG 引导目标选择（对齐 GCC `Analyzer` 能力）**

- **FR-009**: 系统 MUST 从被测 Clang/LLVM 获取目标函数的控制流结构（基本块、后继关系、每个基本块关联的被测编译器源码行号），作为目标选择的输入。
- **FR-010**: 系统 MUST 在该控制流结构上构建与 GCC Analyzer 等价的索引（行→基本块、基本块→后继/前驱、基本块初始权重=后继数）。
- **FR-011**: 系统 MUST 实现与 GCC 等价的目标 BB 选择：候选须位于配置目标函数内、至少含一行未覆盖、且可达（无前驱或至少一个前驱已被覆盖）；按权重排序、平分随机；并在多次失败后对 BB 权重衰减。
- **FR-012**: 系统 MUST 维护"源码行→曾覆盖它的 seed 列表"映射并可持久化，用于为目标 BB 选取锚点 base seed（与 GCC `coverage_mapping.json` 语义一致）。
- **FR-013**: 系统 MUST 在配置目标函数无法在被测编译器控制流结构中匹配时给出明确错误或告警，而非静默产生空目标集。
- **FR-014**: 系统 MUST 在目标函数全部覆盖时返回"无可选目标"信号，使主循环行为与 GCC 一致（进入终态/随机阶段由上层决定）。

**集成与配置**

- **FR-015**: 系统 MUST 让 fuzz engine 通过统一的覆盖率抽象消费 LLVM 与 GCC 两套实现，引擎主循环、corpus、目标选择编排逻辑无需为 LLVM 改写。
- **FR-016**: 系统 MUST 通过配置驱动 LLVM 方案的全部外部依赖路径与命令（被测编译器路径、覆盖率工具命令、原始覆盖产物目录、累计报告路径、控制流结构来源、目标文件/函数列表等），不得在代码中硬编码。
- **FR-017**: 系统 MUST 保证新增 LLVM 方案不改变 GCC 方案的现有行为（无功能回归）。
- **FR-018**: 系统 MUST NOT 修改预言机（oracle）、LLM 变异、prompt 等子系统的语义；本特性的改动范围限定在覆盖率模块及其在引擎装配处的接线。
- **FR-019**: 系统 SHOULD 复用引擎中已有的"统一抽取已覆盖行"入口，使引擎读取覆盖结果时对 GCC/LLVM 报告格式差异无感。
- **FR-020**: 系统 SHOULD 提供一份面向栈保护（canary）策略的 LLVM 示例配置，作为与 GCC 对齐的参考与端到端验证入口。

### Key Entities *(include if feature involves data)*

- **LLVM 覆盖率实现**：满足覆盖率抽象契约的组件，封装"插桩被测 Clang 编译 seed → 采集原始覆盖 → 合并 → 导出可读报告"的流程。关键属性：被测编译器调用方式、运行期覆盖产物位置、累计报告路径、目标过滤配置。
- **LLVM 覆盖报告**：单 seed 或累计覆盖的载体，可序列化、可被解析为"被测编译器源码 file:line 的命中集合"。
- **控制流结构（CFG）数据**：被测 Clang/LLVM 目标函数的基本块/后继/行号信息，作为目标选择输入；与 GCC `.015t.cfg` 在语义上对应。
- **目标基本块（Target BB）**：被选中作为 fuzz 目标的未覆盖基本块，携带函数名、BB 标识、源码行、权重、可达性、关联 base seed 等。
- **覆盖映射（Coverage Mapping）**：源码行→曾覆盖该行的 seed 列表，持久化以支撑断点续跑与 base seed 选取。
- **LLVM 覆盖率配置**：驱动上述全部路径/命令/目标的配置数据，与现有 GCC 配置在结构上对应。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在被插桩 Clang 上，引擎对单颗成功编译的 seed 能产出非空的被测编译器源码覆盖报告，命中行集合可被解析为 file:line 列表。
- **SC-002**: 对"已知带来新覆盖"的 seed，系统判定增量为真的准确率为 100%；对"已知无新覆盖"的 seed，判定无增量的准确率为 100%（在受控测试集上）。
- **SC-003**: 累计覆盖在中断后重启能 100% 从既有总报告继续，不出现"覆盖率归零重来"。
- **SC-004**: 给定目标函数控制流结构与已覆盖行集合，目标 BB 选择产出的候选 100% 满足"在目标函数内、含未覆盖行、可达"三项约束。
- **SC-005**: 同一套上层引擎在 GCC 配置与 LLVM 配置下均能完成至少一轮"测量 + 目标选择"，且 GCC 路径相对移植前无行为回归（现有 GCC 相关测试全部通过）。
- **SC-006**: 覆盖率模块以外的子系统（oracle/LLM/prompt）的现有测试在本特性引入后全部保持通过，证明改动未越界。
- **SC-007**: LLVM 方案的核心能力（测量、增量判定、合并、目标选择、覆盖映射）均有可独立运行的测试覆盖。

## Assumptions

- 运行环境可获得一个**被插桩的 Clang/LLVM** 作为被测编译器，其构建（插桩选项、待插桩源文件/Pass 范围）由项目外的构建流程产出，类比现有"被插桩 GCC"的构建产物，不在本特性范围内。
- LLVM 原生覆盖率工具（profile/profdata/cov 系列）在运行环境中可用，路径与命令经配置提供。
- 被测编译器目标函数的控制流结构可由某种 LLVM 侧产物或工具获得；其具体获取方式（编译期 dump 或离线提取）在实现规划阶段确定，但语义须等价于 GCC 的 `.015t.cfg`（基本块+后继+行号）。
- 本移植聚焦栈保护（canary）策略的被测编译器源文件/Pass，作为与 GCC 对齐的首个落地点；其他防御机制的扩展不在本特性范围。
- 覆盖率统计采用与 GCC 方案一致的"被测编译器自身源码行覆盖"口径，而非 seed 程序覆盖。
- 引擎已存在的覆盖率抽象与"统一抽取已覆盖行"入口可被复用或最小化扩展以容纳 LLVM 实现，不需要重写主循环。
- 论文中的覆盖率方案在本项目按"简化版"落地：仅行/区域级覆盖反馈 + 基本块级目标选择，不实现论文的高级反馈/全局分析特性。
